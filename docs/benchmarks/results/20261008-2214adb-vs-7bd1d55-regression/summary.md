# 2026-10-06～08 性能回归报告

## 结论与适用范围

四批正式 ABBA 测量均已完成，**整体性能验收未通过**。Redis 关键路径出现吞吐下降、
尾延迟和分配增加；Redis binary 大 Value 也有退化信号。Valkey 波动明显，部分 P99 变差；
Codec 分配基本持平，不能据此排除其他路径的开销。

本报告对比基线 `2214adb` 与候选 `7bd1d55`，共同 harness 为 `7bd1d55`。
它不是 Maven Central 已发布 `0.1.0-alpha.1` 制品的重新测量，也不是当前工作树的性能证明。
对比覆盖两次提交间的全部改动，不能把差异归因于单个阶段。

| 未覆盖 | TLS 性能、全 workload/JDK/OS 矩阵、跨主机分区、生产长稳 |

完整提交 SHA、当批构建产物 SHA-256、镜像 digest 与 runner 参数在各批的
`raw/<run-id>/build-manifest.txt`、`environment.txt` 中。不同批次分别构建，
产物哈希不同；不要仅凭短提交号假设 JAR 字节完全相同。

启动时负载/核门禁上限为 1.50。Critical 为 1.139，Redis binary 约 1.111；
Valkey 为 0.781。Codec 外层预检为 1.059；其 environment 内层记为 `not_run`，
不能把内层记录误当作执行过独立预检。没有连续宿主负载证据证明全程空闲。
10 月 6 日后续 Valkey 启动曾因 3.447 超限而停止，原失败仍保留在实施记录；
10 月 7 日恢复的是剩余批次，不是重跑或替换已完成的 Redis 测量。

配对一为 B02/A01，配对二为 B03/A04。汇总变化为
`(B02 + B03) / (A01 + A04) - 1`，不是两个配对比值的简单平均，也不是显著性检验。
吞吐越大越好；P99、allocation 越小越好。P99 是各 run 分位数的均值比，
不是合并样本 P99。吞吐与延迟分开运行，不把不同时间段的改善合并成单一收益。
Pipeline 吞吐与延迟均按命令归一化，不是整批值。

## 5. 诊断与下一步

独立 Raw Pipeline 构造探针只入队、不 execute；ABBA 各 JVM 预热 20,000 批，
五次测量各 20,000 批、每批 128 GET，ThreadMXBean 计调用线程分配，固定堆 128 MiB。
基线为 64.5 B/command，候选为 88.8125 B/command，增加 24.3125 B/command；
重复运行一致。这证明构造额外分配存在，**不等于解释端到端下降幅度**，也不是 JMH 吞吐验收。
[探针源码](diagnostics/BobaAllocationProbe.java)与[重复运行输出](diagnostics/pipeline-construction-allocation.log)已保留。

源码审查还发现发送前临时参数数组和重复校验、text typed 双层准入、普通请求使用专用取消包装等
优化候选，尚未全部量化因果。下一步应先拆分额外分配与环境波动，保持参数所有权、
Raw 准入、FIFO 和失败语义，再逐项优化、受控复测。不能删除安全检查或放宽测试断言来制造提升。
本次归档未改核心、未启动新测试或压测。
